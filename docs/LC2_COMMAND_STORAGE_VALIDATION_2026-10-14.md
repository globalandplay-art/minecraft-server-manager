## Implemented scope

- Version1 strict backend-only records, at most4096 bytes each and32 checkpoints/operation. Exact fixed fields, valid UTC timestamps, stable operation/server/request/key/runtime/root/guard bindings, prior-record digest and state-transition verification. No paths, plaintext keys, credentials or command stdout/stderr in records.
- Lazy private `whitelist-commands` namespace and root admission anchors. Open/scan are read-only; creation happens only on a trusted already-admitted caller's write. Defaults use existing Windows private ACL creation/no-replace publication and ManagerLifetimeLock unchanged. Trusted test construction may inject Fake publication/ACL; no environment variable or request enables them.
- Exact bigint root/directory/file identities, canonical containment, no symlink/junction/hardlink, bounded complete descriptor reads, before/after ACL and identity checks, temporary buffer zeroing including failure. Known same-content replacement/deletion is detected within a store instance. Storage reads and writes use one owner mutation lease, so a concurrent scan returns BUSY instead of inspecting a writer's transient stage.
- Root anchor binds genesis; every appended checkpoint has a separately published immutable root witness with exact sequence/hash. Witness precedes checkpoint. Missing/extra/mismatched witnesses or checkpoints, stages, unknown files/versions, duplicate keys/owners, broken chains or ambiguous publication fail closed; no repair/deletion/truncation. A failure after namespace-only publication may leave a valid empty namespace, never an operation success; common admitted-operation reconciliation is still required before future business writes.
- Global default10000 scan-entry bound, including root inventory and command evidence. Capacity is reserved before publication. Trusted constructors can only lower this limit (minimum3), not exceed it. Capacity/conflict rejects have zero publication and preserve readable history. No TTL or retention: same server/key/request returns original head across a new store and arbitrarily later timestamps; different request conflicts. Replay does not dispatch.
- Fixed storage errors with no filesystem path/cause/ACL snapshot or original exception. BUSY/key-conflict/capacity remain distinct. Unsafe disk/ACL/publication faults poison the instance; invalid caller transitions with unchanged evidence do not rewrite history.

## Deliberately not implemented / not proven

The only recorded states are intent-persisted, dispatch-intent, response-recorded and recovery-required. NONE is a success terminal or authorization to dispatch, resend or clear recovery. All existing nonterminal history after restart must require inspection at the future coordinator. A response hash or guardReceiptHash is a binding supplied by a trusted caller, not proof of response semantics, guard persistence or causality. This store does not read/create the member-byte guard and cannot settle explicit recovery.

Same-user administrators can remove a matched suffix checkpoint+witness pair or all evidence while the process is dead; local immutable records cannot independently prove that such evidence existed. Current in-memory known identities detect those deletions while open, but a new store cannot. No automatic dispatch/resumption is permitted from the remaining prefix, including genesis-only replay. Stronger trusted high-water anchoring, if required, is a separate design Gate. Preserve this limit in all future startup/recovery decisions; do not call a surviving prefix proof of complete history or non-dispatch.

Publication injection tests reopen a new store object, not a fresh OS process. They prove scan/model reconstruction only, not process-death durability. Actual Windows native ACL/publication integration for THIS store, child-process crash tests and power-loss durability are NOT RUN. Existing native primitive tests remain historical evidence, not a substitute. Common Operation pairing, protection-byte guard, generation-bound RCON/no-stdin, real Vanilla grammar, causal outcome verification, explicit recovery and member UI remain pending.
