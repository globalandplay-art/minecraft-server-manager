## Implementation

- `WhitelistOnlineService` is the default local app path. It reuses `WhitelistService`, `PropertiesReader`, safe fixed-file readers, registry identities, `OperationService.runExclusive` and `openWhitelistSession`. The old coordinator factory remains test-only/injected, not the production default.
- Both candidate and manual additions call the same POST member API. Names are strictly ASCII Java names, 3–16 characters. UUIDs are read from Minecraft's files and never generated by the mutation service.
- Requests recheck registered-root identity, current file/revision, live membership and the owned runtime generation. Lifecycle and member actions share exclusion. Each RCON session can mutate only once, without stdin fallback or automatic reconnect/resend of an uncertain command.
- Success requires the matching native response, the exact intended membership change with unrelated members unchanged, live names matching the new saved list, a healthy owned process, and bounded direct log observation. A response of `executed`, no ERROR, or list equality alone cannot prove success.
- Logs: one fixed `logs/latest.log` descriptor is held for this operation. Root/directory/file identity, single-link status, offsets and stable complete UTF-8 lines are checked. At most 64KiB of newly appended bytes are inspected. Missing/rotated/truncated/unsafe/oversized/partial windows fail before send or return UNKNOWN after send. The exact StoredUserList save-failure messages at Server thread WARN/ERROR are relevant; ordinary warnings/unrelated errors are not attributed to the whitelist action. No IP/raw logs are returned or retained.
- Candidates are dynamically read from the selected root's bounded `usercache.json`. Duplicate names are normalized, conflicting name/UUID associations make the source unavailable, existing saved members are excluded. Historical cache data does not verify current account identity. No application database or approval queue exists.
- Visible-page polling is every 5 seconds. Whitelist and candidate requests run sequentially; a pending query is not overlapped by another interval. Hidden pages stop polling, switching instances aborts/isolate old reads, failed reads preserve old snapshots and disable mutation. UNKNOWN stays blocked until an explicit manual refresh; no refresh resends a mutation.
- Same-key duplicates share a bounded process-local result; no durable exactly-once or crash replay is promised. No new command journal, native helper, GuardStore or persistent task framework is used.
